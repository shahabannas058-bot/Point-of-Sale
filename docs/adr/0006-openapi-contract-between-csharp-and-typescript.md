# ADR-0006: OpenAPI as the contract between C# and TypeScript

**Date**: 2026-10-18
**Status**: accepted
**Deciders**: Owner, Claude

## Context

With a C# server and TypeScript clients (desktop app, React admin panel, later owner PWA), the Zod schemas in `packages/shared` can no longer be shared with the server. We need one source of truth for requests and responses so the two sides cannot drift apart silently. OpenAPI is a plain spec file generated by the server; no API key or external service is involved.

## Decision

The ASP.NET Core server publishes an OpenAPI document. A TypeScript client in `packages/api-client` is generated from it (openapi-typescript or NSwag) and is never hand-edited. Rules implemented on both sides (invoice hash chain, stock ledger, money, quantities) are checked with shared JSON test vectors that both vitest and the .NET tests run. The admin panel is React + TypeScript and uses this generated client.

## Alternatives Considered

### Alternative 1: Hand-written types on both sides
- **Pros**: no tooling
- **Cons**: they drift; bugs appear only at runtime
- **Why not**: too error-prone

### Alternative 2: gRPC / protobuf
- **Pros**: strong typing, fast
- **Cons**: awkward from browsers and Tauri webviews, heavier tooling
- **Why not**: REST + OpenAPI is simpler for this team and clients

## Consequences

### Positive
- Changing an endpoint breaks the TypeScript build immediately instead of failing in production

### Negative
- An extra generation step in the build

### Risks
- Forgetting to regenerate the client; mitigated by a CI check that the generated file is up to date
